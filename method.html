核验方法

这一页说明每条核验是怎么做出来的、什么算通过、什么不算——**你不需要相信我们，你可以照着复现**。

四级核验，逐级加严

级别做了什么能证明什么不能证明什么
① 文档核验读 README 原文、npm registry 元数据、仓库声明作者声称它做什么、许可证、版本、维护者实际能不能装、能不能跑
② 安装实测在隔离 profile 里真装一次，记录版本与耗时包能解析、能装进 DSH 的插件体系装上之后能不能用、有没有副作用
③ 启动核验用最小 profile 启动一次，看是否报错、是否 pending它能被组合、启动期不炸功能是否正常、隐私行为
④ 运行实测装完真跑一轮具体任务这个功能在真实场景下可用本站目前尚未系统开展

安装实测怎么做的

# 1. 新建一个只用来测试的 profile（不碰日常 profile）
dsh plugin --profile market-test add 插件名

# 2. 确认它真的进了组合
dsh --profile market-test --dump-config

# 3. 最小启动一次，看有没有 pending / 报错
dsh --profile market-test web --no-open --port 51999

每条核验记录都写明：核验日期、DSH 版本、装到的具体版本、结果、失败原因（如果失败）。这些都在 verifications.json 里可机器读取，字段定义见 verifications.schema.json（JSON Schema 2020-12）。

install.result 有四种取值：installed（装进隔离 profile 并进入组合）、partial（包已落地但未进入 profile bundles，例如 pnpm 拦截构建脚本）、failed、not-tested。

版本会过期，所以我们标出来

插件更新很快：2026-11-19 的一次采集里就有 48 个插件发了新版本。所以每条核验记录两件事：核验当时的版本与当前最新版本。

  • 卡片出现「已更新 vX.XX」= 判断基于旧版本，可能已不适用
  • 核验表有「版本状态」列：最新 / 已更新至 x / 未记录
  • 机器可读字段：reviewedVersion、currentVersion、stale

看到「已更新」怎么办：按安装避坑自己装一次，或到讨论区说一声，我们会重新核验。

什么算"通过"，什么不算

  • ✅ 算：装成功、dump-config 里出现、启动不报错
  • ❌ 不算：装成功就写"可用"；启动成功就写"没风险"；README 说得好就写"推荐"
  • ⚠️ 特别注意：安装成功 ≠ 功能正确。站点上所有"已核实"只指可安装性

已知局限（请当成风险提示读）

  • 没有抓包验证：隐私分级（🟢/🔴）是读 README 与权限描述后的判断，不是网络层证据
  • 没有代码审计：风险分级不等于安全结论，高危插件只标注、不背书
  • 单一环境：只在本机 Windows + DSH 0.2.2-rc.3 上测，不覆盖其他平台与旧版本
  • 网络会影响结果：GitHub 源安装受网络影响，超时可能被误判成"装不上"（记录里会写耗时）
  • 只测一个版本：插件升级后结论可能失效，所以每条都标日期

我们踩过的坑（也是你该知道的）

  • 坏包污染：一个 tarball 截断的包写进 lockfile 后，同 profile 之后所有安装都会失败
  • 并发安装冲突：同一 profile 同时跑两个安装会互相破坏，必须串行
  • 看起来一样、其实没装：包在 node_modules 里但 dump-config 没有 = 装了没被组合

处理方式写在 安装避坑指南 里。
