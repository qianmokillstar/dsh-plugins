# 收录与审核标准

## 收录门槛（进目录的硬条件）

1. 仓库或 npm 包能证明它是 DSH 插件，三选一：
   - 仓库根 `package.json` 声明了 `dsh` 字段（bundle / client / profile）
   - 仓库自带 `cordis.patch.yml`
   - npm 包声明了 `dsh.bundle.patch`
2. 只有 README 提到安装方式、拿不到包声明的，可以收录，但**必须标"未核实"**，不得标"已核实可安装"。
3. 仓库必须公开可访问，且最近 12 个月有推送（僵尸仓库只留档、不进主列表）。

## 核实等级

| 等级 | 判定依据 | 站点展示 |
|---|---|---|
| 已核实可安装 | npm 包声明了 `dsh.bundle.patch` | "已核实可安装" |
| 已核实（仓库声明） | 仓库 `package.json` 有 dsh 字段，或含 `cordis.patch.yml` | "已核实（仓库声明）" |
| 未核实 | 仅 README 有安装线索 | "未核实" + 详情页醒目提示 |
| 人工短评 | 已写四问判断 | "人工短评" |

## 判断信息的硬要求

每条短评必须回答四问，缺一不发布：

1. **适合谁**——用人群描述，不用"所有人"。至少 2 条具体场景。
2. **解决什么**——写能力，不写形容词。能量化就量化（token、耗时、并发数）。
3. **风险点**——必须至少 1 条"真的会出事"的风险：凭据、隐私、成本、误删、权限、外部依赖。**风险点为空的评测不允许发布。**
4. **替代品**——至少 2 个，含"什么都不装"这个选项（很多场景最优解就是不装）。

## 风险分级口径

- **低**：只读元数据或界面渲染；崩溃不影响数据；不触网或只读网络。
- **中**：需要凭据、会写盘、会发起网络请求、改变会话内容。
- **高**：系统级控制（注册表、进程、键鼠）、可执行任意代码、凭据集中管理、不可逆操作。

分级是**读 README 后的判断，不是代码审计**。高危插件的评论文末必须写明"未做代码审计"。

## 数据核对（每条都要能回溯）

- 版本、发布时间、许可证、维护者：npm registry 文档。
- 周下载量：npm downloads API，标注统计区间。
- 功能描述：包 README 原文，原文留存在 `data/readmes/`。
- 竞品/替代品：必须在本次采集池或官方内置包清单内出现，不凭印象写。

## AI 使用上限（执行规则）

- 每个审核批次（一周）**最多 10 个插件**进入精读队列。
- 每个插件**最多 1 次** AI 摘要调用；摘要只用于压缩 README 事实，**不允许 AI 下"推荐/不推荐"结论**。
- 结论、风险分级、四问结构由人工确认；AI 产出的段落必须经过事实抽查（版本号、许可、能力清单逐条对原文）。
- 任何 AI 生成的文案不得直接发布，必须经人工改写或确认。
- 批次的 AI 调用记录（插件名、时间、用途）记在发布日志里，便于复盘成本。

## 不收录清单

- 明确要求关闭系统安全机制、或引导用户绕过权限模型的插件。
- 收集用户数据但没有说明用途/存储位置的插件。
- 只有壳、功能与描述不符的包。
- 冒用官方名义但无官方关系的包（community 类会单独标注"社区项目，与官方无关"）。

## 复核节奏

- **每周**：看一次 maintained 状态（最近发布、issue 响应），超过 6 个月不更新的插件在卡片上标注。
- **每月**：重跑 `harvest.mjs`，比对下载量与版本变化；许可证变更必须当天更新。
- **每季**：重读已审核插件的 README，确认四问结论仍然成立。
